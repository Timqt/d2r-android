## Current state (read first when resuming)

**2026-10-23 (round five): Mali (Dimensity / Immortalis) runs on a real device, and the "3D scene is black" bug is root-caused and fixed. Verified on two Xiaomi devices.** ① **Platform**: added support for **Mali-G925-Immortalis MC12** (Xiaomi 25079RPDCC tablet, Android 16, Vulkan 1.3.278, **no root**). Measured limits: `subgroupSize` is 16 only (`EXT_subgroup_size_control` min=max=16, so the package's `host-subgroup-size.txt` must say 16), **every BC format reports `optimalTilingFeatures = 0`** (nearly all game textures are BC, so they are decoded to uncompressed on the CPU via `dm/gfx/tex/nvn_bcdec.c`, the same path the Metal backend uses), GPU timestamps are unsupported (falls back to the CPU clock), `maxComputeWorkGroupInvocations` is 1024. **Re-translating the shaders for the 16-lane profile is wasted work** — the same shader compiles to byte-identical SPIR-V for 64 and 128 lanes (Ryujinx emits runtime-adaptive code), so a new GPU only needs that one file changed.
② **Crash 1: BC textures** — the driver SIGSEGVs on them; the port now has a no-BC path.
③ **Crash 2: once believed to be "3D storage images always crash"** — disproved on 2026-10-23 with a standalone minimal program (the same SPIR-V builds for 3D/2D, at any LocalSize Z, with or without `requiredSubgroupSize`); the real cause back then was a **diagnostic that re-locked `queue_lock` and deadlocked the whole process**. **`local_z_fold` (folding the compute's LocalSize.z down and growing dispatch.z by the same factor) is genuinely required** — turning it off still reproduces the signature crash (`addr=0x18`, `x5=0x7367616c662e656c` = ASCII `le.flags`).
④ **The real bug this round: the 3D scene was almost entirely black while the UI, health orbs and inventory were perfect.** Measured: camp scene area mean sRGB **5.2**, 68% pure-black pixels (the same scene on Adreno: 43.4). **Not the resolution, not the in-game time of day, and not a "skipped compute"** — `552f45c348a61b86` was verifiably built and dispatched. The root cause is that the **LocalSize Z fold invalidates the shader's hand-computed Z index**: the fold only rewrites `OpExecutionMode LocalSize.z` (8→4) and multiplies dispatch.z by 2, which leaves the driver's global z range intact, but these computes **do not use `gl_GlobalInvocationID`** — they compute `(WorkgroupID[2] << log2(LocalSize.z)) + LocalInvocationID[2]` themselves, with the shift amount 3 hardcoded. After the fold the hand-computed z only lands on {0-3, 8-11, 16-19, 24-27}: **half the z slices are never written** (the rest is dropped by the shader's own bounds check), so the computes that write 3D textures (the 32×8×32 light grid, the 32³ colour LUT) fill only half of it, the 3D world loses its ambient light, and the UI is unaffected because it is composited after tone mapping. **The original comment's "the product is unchanged, so the Z semantics are equivalent" argument only holds for shaders that use `gl_GlobalInvocationID`** — that was the biggest detour of this investigation. Fix: rewrite the Z shift to `<<log2(MALI_LOCAL_Z_TARGET)` while folding (new `dm/android/native/nvn_vulkan_zfold.inc`), so the hand-computed z equals the driver's global z, every slice is written exactly once, and the folded shader is **equivalent to the unfolded one**; x/y are untouched because their LocalSize did not change. Standalone test `dm/android/tests/zfold_test.c` (runs on the host, 3/3 PASS). **After the fix**: camp scene area mean sRGB **45.4**, pure black **0%** (Adreno reference 43.4).
⑤ **Two traps worth remembering**: `gl_WorkGroupId` must be identified by its **BuiltIn decoration** (`OpDecorate %var BuiltIn 26`), **not by its position in the OpEntryPoint interface list** (the order of WorkgroupId/LocalInvocationId differs between shaders — `2988a1dc` has it reversed); and **6 computes** are foldable (filter the package's `*.res.json` `local` field for `z>4`: `1188eaed`(8,1,8), `2988a1dc`, `552f45c3`, `73a87ffb`, `890de4b2`, `de7267a5`) — **fixing only 4 of them leaves a gap** (those two simply did not dispatch in the camp).
⑥ **Reusable method**: start from a **same-scene screenshot from another device in the same project** as the baseline (that alone separates "device difference" from "time regression" and disproved the "the user changed the resolution" guess), then **disassemble the real SPIR-V** (`spirv-dis`; do not trust an equivalence argument in a code comment), then **A/B without rebuilding** (the shaders are read from the data package at run time, the package has no per-file digest and the byte count does not change, so replacing the `.spv` files on the device tests the hypothesis directly), and treat the device log + `dumpsys` + `screencap` together as the evidence.
⑦ **Windows build chain fixed**: `build_gpu_driver.py` / `build_gpu_fixtures.py` imported `fcntl` unconditionally (Linux-only) and now fall back on ImportError; the build scripts need `PYTHONUTF8=1` to read their UTF-8 files; `--version` takes `0.6.57` (the script appends `-android-port` itself, `versionCode` = 0×10000+6×100+57).
⑧ **Devices tested**: the Xiaomi 25079RPDCC tablet (Mali-G925-Immortalis MC12, 3008×1880, Android 16, no root) and the Xiaomi M2007J1SC phone (Snapdragon 865 / Adreno 650, Android 12) both run the whole flow — import the package → launch → main menu → character select → camp renders.

- Reported issues fixed and verified on device (2026-10-17): (a) **D-pad and triggers** — Xbox pads report the D-pad as `AXIS_HAT_X/Y`, and the native input path read only the stick axes and dropped HAT entirely, so it did nothing; HAT axes are now mapped to button bits at a ±0.5 threshold in their own bitmask (`dm_pad_hat_buttons`), and the source check accepts `JOYSTICK|GAMEPAD` so a GAMEPAD-source D-pad no longer falls into the touch branch and gets read as a finger position. The same gap existed for the **triggers**: an Xbox pad reports LT/RT as analogue axes (`AXIS_LTRIGGER`/`AXIS_RTRIGGER`, 0-1, flat region 0.062 on this pad) rather than L2/R2 keycodes, so the keycode branch never saw them; they are now read as axes (`AXIS_BRAKE`/`AXIS_GAS` aliases as a fallback) with a 0.5 threshold and their own bitmask (`dm_pad_trigger_buttons`). All three input paths (HAT axes, trigger axes, keycodes) now log on change, so this class of bug can be read straight out of the log instead of guessed at. Verified per button rather than "it seems to work": the game's own `GetNpadState` receipts return exactly the bits that were pressed -- left 0x1000, right 0x4000, up 0x2000, down 0x8000, ZL 0x100, ZR 0x200, LB 0x40, RB 0x80, A 0x1, B 0x2, START 0x400, SELECT 0x800 -- and the threshold behaves as designed (0.41/0.47 do not trigger, 0.66/1.00 do). Host test `t_padmap` is now 36 cases (9 HAT + 7 trigger). The virtual stick hides while a pad is attached and comes back when it is removed, confirmed in the same round by screenshot. Found on the way: the launcher rewrote `launch-settings.conf` and **silently dropped keys it does not own** (that is how `input_receipts=1` was lost and the receipts were never produced); it now carries foreign lines over verbatim. The virtual stick hides while a physical gamepad is attached, found with a device-level `InputManager.InputDeviceListener` because NativeActivity attaches the `AInputQueue` to the main Looper and window dispatch never sees pad events. (b) **Save on background** — the order was wrong: `onPause` suspended graphics, which parks the game thread outside NVN, so the save requested right after could never commit (device log: 0 commits in 3 s, one red "exited without saving" line); the game's own autosave is every 5 minutes, so the worst case was losing nearly that much. Requesting the save first and suspending after (inside the window detach) now gives **2 commits in 241-262 ms**. The guest clock is frozen across the background as well (measured: 18 s in the background advanced the guest clock by only **7.0 s**, exactly the 420 frames actually presented, instead of jumping over the whole period). (c) **Process restarts on background** — a destroyed window no longer ends the process; the surface, swapchain, semaphores and `screen_images` were split into `screen_create_swapchain`/`screen_release` so they can be rebuilt for a new `ANativeWindow`. A real race was found and fixed on the way: Android hands the window over **after** `onResume` (device log order: 图形恢复 → 窗口重建), so the game thread was already running and could be reading the old swapchain while it was rebuilt — the comment claimed "call only while suspended" but the code did not do it. `mtl_screen_attach` now suspends first (`gfx_enter`/`gfx_leave` wait out the present in flight) and the front end releases it based on the foreground state. The duplicate second save request on the exit path was removed (graphics are already suspended there, so it can never commit — it only wasted 3 s and logged a false red line). On device: PID unchanged throughout, 23-24 new present records after the return (~59.9 FPS), normal exit saves in 241 ms and the old process exits cleanly in 1.30 s. `dm_3d_scale_resumed()` was mirrored from iOS on return (otherwise the slow recovery frames are read as GPU pressure and the 3D internal ratio is lowered), and the debug thread now prints a lifecycle line every 10 s (`运行状态 frame=… 3D=… 客体时钟=…`).

- Save import/export (2026-10-17, requested by the user; launcher and in-game menu): export zips the whole internal `files/save/` tree (character / shared stash / Settings, 17 files on this device) through the system "create document" picker, so the player chooses where it lands (Downloads, storage root, anywhere) and the app needs no storage permission. - Re-entering after a background switch (2026-10-17, reported by the user as "press it to the background, go back in, and the game terminates"): the background/resume path itself was fine — process retained, window and swapchain rebuilt, guest clock not jumping. The cause was the **task stack**. The launcher is this app's entry activity, so after a background switch, tapping the icon from the home screen makes Android push a *second* launcher instance on top of the game; the task ends up as launcher(root) / game / launcher(new), the player sees the launcher so the game looks gone, and tapping "start game" then creates a third activity and destroys the game one in the middle. Destroying the game activity ends the whole process in this project (one guest per process), which takes the new activity down with it, after which Android starts a fresh process and reloads from scratch — the "the app terminated and the session is gone" symptom (saves are safe: going to the background already saved). Reproduced on device: PID 26997 before the tap, 28545 after — a new process, with the log truncated by the new instance. Fix: whenever the game activity is still alive (a static flag `D2RActivity.hostRunning`, paired with activity creation and destruction in the same process), the launcher finishes itself at once from `onCreate`/`onResume`, revealing the game underneath and going through the already-verified background-return path. Verified on device: PID unchanged (30764) across HOME and a re-entry through the app icon, window rebuilt, 25 new frames, and no new boot timeline, i.e. no reload. Trade-off to know about: while a game is running the launcher is no longer reachable — to change settings (resolution, another package) swipe the app away from recents first, which is a real exit.

- This round's new warm-up (installed and verified): `dm/android/native/nvn_vulkan_warm.inc` records every genuine graphics pipeline creation to a private `pso_vk_user.tsv` (vs/fs keys, pass key, pipeline key) and, at the end of initialization on the next launch, rebuilds them on a background thread (create then destroy, leaving the compilation in the driver pipeline cache), waiting at most 15 s at the first run-entry loading screen. Manifests carry a version/struct-size header and are ignored wholesale on mismatch; the warm thread only ever loads non-fatally and skips suspicious records. Switches: `DM_PSO_MANIFEST=off` disables warm-up, `DM_PSO_USER=off` disables recording. Runtime and warm-up share one creation function, so dynamic state (viewport/scissor/blend constants/depth bias/stencil masks) never enters the pipeline and both hit the same driver cache entry.
